### 2.2 Routing (React Router Data Mode)

All routes defined in `/routes.ts` using `createBrowserRouter`. Root layout is `AppShell` (sidebar + topbar + language switcher). Authentication enforced via `AuthGuard`. Every CRM route is additionally guarded by a role-specific or feature-specific guard wrapper.

**Guard hierarchy:**

| Guard | Allowed Roles |
|-------|--------------|
| `AdminGuard` | admin |
| `SupervisorGuard` | admin, supervisor |
| `StaffGuard` | admin, supervisor, accountant, front\_desk, marketing |
| `FinanceGuard` | admin, supervisor, accountant |
| `CRMGuard` | admin, call\_center, supervisor, front\_desk, marketing, mentor, teacher, accountant |
| `FeatureCRMGuard` | CRM roles + dynamic FACS check |
| `TeacherGuard` | teacher |
| `StudentGuard` | student |
| `MentorGuard` | mentor |
| `CourseViewGuard` | all authenticated roles |

### 2.3 State Management (localStorage Mock Stores)

Each domain has a dedicated store in `src/lib/`. All follow the same reactive publish-subscribe pattern and are designed for zero-friction migration to real API calls via `api.ts`.

**Pattern:**
```typescript
let data: T[] = [];
const listeners = new Set<() => void>();
function notify() { listeners.forEach(fn => fn()); }
export function subscribe(fn: () => void): () => void { listeners.add(fn); return () => listeners.delete(fn); }
export function getAll(): T[] { return data; }
export function seed(): void { /* idempotent demo data */ }
```

### 2.4 Validation Layer (Zod)

All data parsing uses Zod schemas from `src/lib/schemas.ts` (77 named schemas). Zero `as any` casts in the codebase. The deprecated `safeJsonParse<T>` has been fully migrated to `zodParse`.

```typescript
import { zodParse, zodValidate } from '../lib/error-utils';
import { LeadCardSchema } from '../lib/schemas';

// Safe parse with fallback — never throws
const lead = zodParse(LeadCardSchema, rawJson, fallbackValue);

// Validated parse — returns { success, data, error }
const { success, data, error } = zodValidate(LeadCardSchema, input);
```

### 2.5 Internationalization (i18n)

Three-language support (English, Farsi, Arabic) with full RTL support via the `useLanguage()` hook:

```typescript
const { language, setLanguage, t, isRTL } = useLanguage();

// Key-based lookup (src/translations/{en,fa,ar}.ts)
t('dashboard');  // → "Dashboard" | "داشبورد" | "لوحة القيادة"

// Inline pick for component-level strings (most common pattern)
import { pick } from '../lib/useTranslation';
const label = pick(language as Lang, 'English', 'فارسی', 'العربية');
```

**CSS directional rules (P0 audit completed):**
- Use logical properties only: `ms-4`, `me-2`, `ps-`, `pe-`, `text-start`, `text-end`, `border-s`, `border-e`
- Never use `ml-`, `mr-`, `pl-`, `pr-`, `left-`, `right-` (break RTL layout)
- The `dir` attribute is set on `<html>` based on `isRTL`

Translation files: `src/translations/en.ts`, `fa.ts`, `ar.ts`.

## 4. Security Model

### 4.1 Three-Layer Access Control

**Layer 1 — Route-level Role Guards** (`GuardedCRM.tsx`, `AuthGuard`):
```typescript
const CRM_ROLES = ['admin', 'call_center', 'supervisor', 'front_desk', 'marketing', 'mentor', 'teacher', 'accountant'];
const STAFF_ROLES = ['admin', 'supervisor', 'accountant', 'front_desk', 'marketing'];
const FINANCE_ROLES = ['admin', 'supervisor', 'accountant'];
const ADMIN_ROLES = ['admin', 'supervisor'];
```

**Layer 2 — FACS (Feature Access Control System)** (`feature-permissions-store.ts`):
Granular boolean matrix of `feature_key × role`. Admins can toggle features per role at runtime from `/admin/feature-access`. Changes persist in localStorage and take effect immediately without reload.

**Layer 3 — In-page data filtering** (via `useAuth()` + role checks):
CRM pages filter displayed records based on the current user's role — teachers see only their own classes; call center agents see only their own leads.

Key security boundaries:
- **Teacher:** CRM access for own classes only; no financial data; no staff panels
- **Student:** Learning portal only; no CRM; no admin
- **Call Center:** CRM pipeline + VoIP; no financial reports; filtered by agentId
- **Accountant:** Financial pages view-only in CRM; no pipeline actions

### 4.2 Authentication

- **Session storage:** Auth state in `sessionStorage` via `AuthContext` (clears on tab close)
- **JWT tokens:** Backend API requests authenticated via Bearer token
- **OTP login:** Kavenegar SMS — 6-digit code, 5-minute TTL, rate-limited (3 requests / 10 min per phone)
- **PIN 2FA:** Admin/supervisor secondary PIN check
- **DevRoleSwitcher:** `src/components/dev/DevRoleSwitcher.tsx` — disabled in production via env flag

## 5. Real-Time Communication

### 5.1 Socket.IO (Server → `/server/socket/index.ts`)

| Event | Direction | Purpose |
|-------|-----------|---------|
| `room:join` | client → server | Student/teacher enters a class room |
| `room:leave` | client → server | Participant exits |
| `room:participant-joined` | server → clients | Broadcast join event |
| `room:participant-left` | server → clients | Broadcast leave event |
| `message:send` | client → server | Send chat message |
| `message:received` | server → clients | Deliver message to recipient |
| `typing:start` / `typing:stop` | bidirectional | Typing indicators |
| `presence:update` | client → server | Online/away/busy status |
| `notification:new` | server → client | Push notification to user |

### 5.2 WebRTC / CallerN

- **Signaling:** Socket.IO (room-based, via `room-signaling.ts`)
- **Peer connections:** WebRTC `RTCPeerConnection` with STUN/TURN config from `webrtc-store.ts`
- **Auto-attendance bridge:** `RTCPeerConnection.onconnectionstatechange === 'connected'` → `room-signaling.ts` → `auto-attendance-store.recordJoin()`
- **CallerN discovery:** `callern-store.ts` handles teacher-student matching, credit deduction, session lifecycle
- **Video call room:** `src/components/callern/VideoCallRoom.tsx` + `SessionRoom.tsx`

### 5.3 Webhook Notifications

Attendance alerts delivered to external channels via `webhook-notifications.ts`:
- **Telegram Bot API** (chat\_id + bot token, configurable per institute)
- **SMS gateways** (Kavenegar, Melipayamak, or custom webhook endpoint)
- Full delivery log stored in localStorage with severity levels (`critical`, `warning`, `info`, `success`)

### 6.1 Supported Gateways

| Provider | Type | Status |
|----------|------|--------|
| Zarinpal | Iranian (Shaparak) | Primary |
| IDPay | Iranian (Shaparak) | Supported |
| Zibal | Iranian (Shaparak) | Supported |
| Mellat | Iranian (Shaparak) | Supported |
| Tejarat | Iranian (Shaparak) | Supported |
| Stripe | International | Sandbox only |

Active gateway and credentials configured at `/payment-gateway-config` (admin-only). Sandbox mode per gateway. All transactions logged in `payment-gateway-store.ts`.

### 6.2 Payment Flow

```
Student Checkout → Gateway Redirect → /payment/gateway (ShetabGatewaySimulator in dev)
               → Payment Callback → /payment/callback → PaymentCallback.tsx
               → PaymentRecord stored in payment-store.ts
               → emitPaymentReceived() → Accountant notification
```
